# v0.4.2 — Data Integrity & Cycle Editing

**Status**: COMPLETE
**Branch**: `feature/encryption`
**Parent**: Milestone 1 (Notification Reliability, v0.4.1)

---

## Problem Statement

The cycle data model has no editing capabilities. Users can add cycle start entries but cannot delete or correct them. There are also no constraints preventing duplicate or overlapping entries at the storage layer.

### Current Gaps

1. **No delete**: `CycleLogScreen` renders entries as read-only cards. The `Repository` interface has no `deleteCycleStart()` method.
2. **No edit**: No way to correct a mistyped date. Users must live with errors or lose all data.
3. **No duplicate prevention at storage layer**: `addCycleStart()` in both `realmRepo.ts` and `memoryRepo.ts` will accept the same `(profileId, startDateIso)` pair multiple times, creating duplicate entries. Only `quickLogCycleStart()` performs a client-side dedup check, and only for the Dashboard quick-log path — `CycleLogScreen.onAddCycleStart()` has no dedup guard.
4. **No notification resync after mutation**: When editing capabilities are added, cycle data changes must trigger `syncNotifications()` to recalculate predicted dates and reconcile alarms.
5. **Cycle length computation assumes sorted, unique dates**: `computeCycleLengths()` filters out `diff <= 0` entries but doesn't warn. Duplicate dates produce zero-length gaps that are silently discarded, which is correct behavior but fragile if duplicates accumulate.
6. **Sorting responsibility on callers**: `typicalCycleLength()`, `computeCycleLengths()`, and `buildNotificationPlan()` all assume pre-sorted ascending input. Every caller (`loadDashboardData.ts:52`, `syncNotifications.ts:83`) must remember to `.sort()`. If a new caller forgets, predictions silently produce wrong results.

## Data Model Audit

### Storage

| Entity | Schema | Primary Key | Indexed |
|---|---|---|---|
| `CycleStart` | `{ id: int, profileId: int, startDateIso: string, createdAt: string }` | `id` (auto-increment) | `profileId` |
| Realm schema | `CycleStartSchema` in `realmRepo.ts:25-34` | `id` | `profileId` indexed |
| Uniqueness | **None** — no unique constraint on `(profileId, startDateIso)` | | |

### Computation Chain (Current — Caller-Sorted)

```
listCycleStarts(profileId)           → CycleStart[] (sorted by id, not date)
  ↓ .map(c => c.startDateIso).sort() → string[] (sorted ASC by ISO string)  ← CALLER RESPONSIBILITY
    ↓ typicalCycleLength()           → median of last N gap lengths (null if < 2 dates)
    ↓ estimateNextStart()            → lastStart + typicalLen days
    ↓ computeCycleDay()              → daysBetween(lastStart, today) + 1
```

### Computation Chain (Target — Single Canonical Sort)

```
listCycleStarts(profileId)           → CycleStart[] (sorted by id, not date)
  ↓ .map(c => c.startDateIso)       → string[] (unsorted — callers pass as-is)
    ↓ computeCycleLengths()          → SOLE SORT POINT: [...dates].sort() at entry
    ↓ typicalCycleLength()           → delegates to computeCycleLengths (no sort)
    ↓ buildNotificationPlan()        → uses reduce() max-comparison for lastStart (no sort)
    ↓ loadDashboardData()            → uses reduce() max-comparison for lastStart (no sort)
    ↓ computeCycleDay()              → daysBetween(lastStart, today) + 1 (unchanged)
    ↓ estimateNextStart()            → lastStart + typicalLen days (unchanged)
```

**Sort ownership**: `computeCycleLengths()` is the single canonical sort point. No other function sorts date arrays. See ADR 0008 D6.

Functions that change:
- `computeCycleLengths(startDatesIso)` — adds `[...startDatesIso].sort()` at entry, renames param (was `sortedStartDatesIsoAsc`)
- `typicalCycleLength(startDatesIso)` — renames param (was `startDatesIsoAsc`), adds `lengths.length < 2` guard (see D7)
- `buildNotificationPlan()` — renames param (was `cycleStartDatesAsc`), uses `dates.reduce((a, b) => a > b ? a : b)` for `lastStartIso` instead of `sorted[-1]`

Functions that do NOT change:
- `computeCycleDay(todayIso, lastStartIso)` — two scalar inputs, no array
- `estimateNextStart(lastStartIso, typicalLen)` — two scalar inputs, no array
- `median(nums)` — already sorts internally (its own domain)

Callers that simplify:
- `loadDashboardData.ts:52-54` — remove `.sort()`, use `reduce()` max-comparison for `lastStart`
- `syncNotifications.ts:83` — remove `.sort()`

### Notification Consumption

```
syncNotifications()
  ↓ repo.listCycleStarts(profileId)
  ↓ cycles.map(c => c.startDateIso)            ← .sort() removed (domain sorts internally)
  ↓ computeNotificationPlan()
    ↓ buildNotificationPlan()
      ↓ sorts internally
      ↓ typicalCycleLength(cycleStartDates) → typLen
      ↓ estimateNextStart(lastStart, typLen) → targetDateIso
      ↓ subtractDays(targetDateIso, daysBefore) → fireDateIso
      ↓ makeReminderId(profileId, fireDateIso)  → deterministic ID
```

**Key insight**: Any mutation to cycle data (add/edit/delete) changes `cycleStartDatesAsc`, which changes `typLen`, which changes `targetDateIso`, which changes `fireDateIso`, which changes the notification ID. Therefore **every cycle mutation must trigger `syncNotifications()`** to cancel stale alarms and schedule new ones.

## Invariants

### Must Always Be True

| # | Invariant | Current Enforcement | Gap |
|---|---|---|---|
| I1 | `startDateIso` is a valid ISO date (YYYY-MM-DD) | `assertIsoDate()` in both repo implementations | None — solid |
| I2 | `profileId` references an existing profile | `realmRepo.addCycleStart()` checks; `memoryRepo.addCycleStart()` checks | None — solid |
| I3 | No two `CycleStart` entries for same `(profileId, startDateIso)` | `quickLogCycleStart()` checks — but only for dashboard path | **Gap**: `CycleLogScreen.onAddCycleStart()` does not check. **Fix**: enforce at repo layer in both `addCycleStart()` and `updateCycleStart()` |
| I4 | Cycle dates are sorted ascending before computation | Consumers call `.sort()` after fetching | **Gap**: fragile caller discipline. **Fix**: move sorting into `computeCycleLengths()` and `buildNotificationPlan()` |
| I5 | After any cycle mutation, notifications are re-synced | Add: yes (6 call sites). Edit/delete: **not possible yet** | **Gap**: no edit/delete capability. **Fix**: wire `syncNotifications()` at all new mutation call sites |
| I6 | `typicalCycleLength` returns null with < 3 cycle starts (< 2 intervals) | Current: returns value with 2 starts (1 interval). | **Gap**: single interval is not a statistical estimate. **Fix**: change guard to `lengths.length < 2` (ADR 0008 D7) |
| I7 | Zero-length cycles (duplicate dates) are discarded from length computation | `if (diff > 0)` guard in `computeCycleLengths()` | None — but duplicates shouldn't exist per I3 |
| I8 | `startDateIso` is not in the future | Not enforced | **Gap**: future dates create broken predictions. **Fix**: enforce at repo layer via `assertNotFutureDate()` (ADR 0008 D8) |

### Impossible States to Prevent

- A cycle start date in the future — **rejected at repository layer** (D8). Throws `FutureDateError`.
- A cycle start with negative gap (< 1 day from previous) — currently silent, `computeCycleLengths()` discards `diff <= 0`
- Orphaned cycle starts (profile deleted but cycles remain) — covered by cascade delete

## Edge Case Behaviors

Explicit specification for boundary conditions. All behaviors below are **by design** and must be preserved by tests.

### Deleting the Most Recent Cycle Start

The "most recent" start is `sorted[-1]` — the last entry chronologically, which serves as the anchor for both `computeCycleDay()` (current day in cycle) and `estimateNextStart()` (next prediction).

| Prior State | After Delete | Dashboard Effect | Notification Effect |
|---|---|---|---|
| 4+ starts, delete most recent | Second-most-recent becomes `lastStart` | `cycleDay` jumps (recalculated from older start). `typicalLength` recalculates from remaining intervals. `nextEstimate` shifts. | Predicted target date changes → fire date changes → notification ID changes → set-diff cancels old, schedules new. |
| 3 starts, delete most recent | 2 starts remain (1 interval) | `cycleDay` recalculates from remaining last start. `typicalLength` → `null` (1 interval < minimum 2). `nextEstimate` → `null`. | All notifications cancelled (below prediction threshold). |
| 2 starts, delete most recent | 1 start remains | `cycleDay` recalculates from sole remaining start. `typicalLength` → `null`. `nextEstimate` → `null`. | Already no notifications (was below threshold). |
| 1 start, delete it | 0 starts | `cycleDay` → `null`. `lastStart` → `null`. `typicalLength` → `null`. `nextEstimate` → `null`. Dashboard shows empty state. | All notifications cancelled (empty plan). |

### Editing the Most Recent Cycle Start

| Change Direction | Dashboard Effect | Notification Effect |
|---|---|---|
| Move date earlier (e.g., 2026-03-01 → 2026-02-25) | `cycleDay` increases (more days since start). Intervals to previous entry change → `typicalLength` recalculates → `nextEstimate` shifts. | Predicted target date changes → new notification ID → set-diff reconciles. |
| Move date later (e.g., 2026-03-01 → 2026-03-05) | `cycleDay` decreases. Same recalculation chain. | Same reconciliation. |
| Edit to same date (no-op) | No change. | No change — `syncNotifications` produces empty diff. |

### Deleting All Cycle Data

When all entries for a profile are deleted (one by one):

| State | `cycleDay` | `typicalLength` | `nextEstimate` | Notifications |
|---|---|---|---|---|
| 0 starts | `null` | `null` | `null` | All cancelled |

Dashboard shows `EmptyState` component: "Log your first period to start tracking."

### Only One Cycle Start Exists

| Metric | Value | Rationale |
|---|---|---|
| `cycleDay` | `daysBetween(start, today) + 1` | Computed from sole entry |
| `typicalLength` | `null` | 0 intervals — need ≥ 2 intervals (3 starts) |
| `nextEstimate` | `null` | Requires `typicalLength` to compute |
| Notifications | None scheduled | `buildNotificationPlan()` returns `[]` when `typicalLength` is `null` |

### Exactly Two Cycle Starts

| Metric | Value | Rationale |
|---|---|---|
| `cycleDay` | `daysBetween(lastStart, today) + 1` | Computed from most recent entry |
| `typicalLength` | `null` | 1 interval — below minimum of 2 intervals (ADR 0008 D7) |
| `nextEstimate` | `null` | Requires `typicalLength` to compute |
| Notifications | None scheduled | Below prediction threshold |

User sees their current cycle day and last start date but gets no predictions or notifications until they log a third start.

### Prediction Data Requirements

`typicalCycleLength(dates, maxN=3)` requires **at least 2 intervals** (3 cycle starts) before returning a non-null value. Below that threshold, predictions and notifications are not generated.

| Cycle Starts | Intervals | `typicalLength` | `nextEstimate` | Notifications | Dashboard Shows |
|---|---|---|---|---|---|
| 0 | 0 | `null` | `null` | None | Empty state |
| 1 | 0 | `null` | `null` | None | `cycleDay` only |
| 2 | 1 | `null` (below threshold) | `null` | None | `cycleDay` + `lastStart` |
| 3 | 2 | `median([a, b])` = `(a+b)/2` | Computed | Scheduled | Full dashboard |
| 4+ | 3 (last 3 used) | `median([a, b, c])` | Computed | Scheduled | Full dashboard |

The `maxN=3` window means old outlier cycles age out as the user logs more data. The minimum of 2 intervals provides a meaningful median (average of two values) rather than echoing a single observation.

### Editing a Historical (Non-Recent) Cycle Start

Editing an older entry changes the interval lengths between it and its neighbors. This **retroactively changes the typical cycle length** and therefore the predicted next start date. This is intentional — the prediction should reflect the most accurate data available. See ADR 0008, "Prediction Recalculation Semantics."

## Editing Capabilities Design

### 1. Delete Cycle Start

**Repository change**: Add `deleteCycleStart(id: number): Promise<void>` to interface.

**Realm implementation**: Delete by primary key within `realm.write()`.

**Memory implementation**: Filter by id.

**UI**: Swipe-to-delete or long-press on `CycleLogScreen` entry cards.

**Post-mutation**: `syncNotifications()` fire-and-forget.

**Edge case**: Deleting the only remaining cycle start (or reducing to < 2) → `typicalCycleLength()` returns `null` → `buildNotificationPlan()` returns `[]` → all existing notifications cancelled. This is correct.

### 2. Edit Cycle Start (Date Correction)

**Repository change**: Add `updateCycleStart(id: number, newStartDateIso: string): Promise<CycleStart>` to interface.

**Realm implementation**: `objectForPrimaryKey` + `realm.write()` to update `startDateIso`.

**Memory implementation**: Find by id, replace `startDateIso`.

**UI**: Tap on entry card → inline edit or modal with date picker.

**Validation**: `assertIsoDate()` + duplicate check against `(profileId, newStartDateIso)`.

**Post-mutation**: `syncNotifications()` fire-and-forget.

### 3. Duplicate Prevention (Repository-Layer Enforcement)

The uniqueness constraint on `(profileId, startDateIso)` is enforced at the repository layer, not the UI layer. This makes it impossible to create duplicates regardless of call path. Violations throw `DuplicateCycleStartError` (ADR 0008 D1).

**`addCycleStart(profileId, startDateIso)`**:
- Realm: `filtered("profileId == $0 AND startDateIso == $1", profileId, startDateIso)` before insert. Throw `new DuplicateCycleStartError(startDateIso)` if match found.
- Memory: `.some(cs => cs.profileId === profileId && cs.startDateIso === startDateIso)` before push. Same error.

**`updateCycleStart(id, newStartDateIso)`**:
- Realm: `filtered("profileId == $0 AND startDateIso == $1 AND id != $2", profileId, newStartDateIso, id)` before update. Throw `new DuplicateCycleStartError(newStartDateIso)` if match found.
- Memory: `.some(cs => cs.profileId === profileId && cs.startDateIso === newStartDateIso && cs.id !== id)` before update. Same error.

**`quickLogCycleStart()`**: Existing duplicate check is retained as a fast-path optimization. It returns `{ status: "already_exists" }` without hitting the repo error path, giving the dashboard a cleaner UX (no error banner, just silent no-op).

### 4. Future-Date Rejection (Repository-Layer Enforcement)

Both `addCycleStart()` and `updateCycleStart()` call `assertNotFutureDate(startDateIso)` before any write. Future dates throw `FutureDateError` (ADR 0008 D8). Today is allowed (boundary: `startDateIso > todayIso` is rejected, `===` is accepted).

### 5. Notification Resync Guarantees

Every mutation triggers `syncNotifications()`:

| Mutation | Call Site | Sync Pattern |
|---|---|---|
| Add (existing) | Dashboard quick-log, CycleLogScreen | Fire-and-forget (already wired) |
| Delete (new) | CycleLogScreen | Fire-and-forget after `deleteCycleStart()` |
| Edit (new) | CycleLogScreen | Fire-and-forget after `updateCycleStart()` |

## Mutation Contract

### `deleteCycleStart(id: number)`

| Step | Action |
|---|---|
| 1 | Validate `id` exists |
| 2 | Delete within `realm.write()` |
| 3 | Return void (idempotent — no error if already deleted) |
| 4 | Caller triggers `syncNotifications()` |

**Downstream effects**:
- `typicalCycleLength()` may change (fewer data points)
- `estimateNextStart()` recalculates from new last start
- Notification IDs change if predicted date shifts
- Set-diff reconciliation cancels stale, schedules new

### `updateCycleStart(id: number, newStartDateIso: string)`

| Step | Action | Error |
|---|---|---|
| 1 | Validate `newStartDateIso` format | `Error` (from `assertIsoDate`) |
| 2 | Validate not future date | `FutureDateError` |
| 3 | Validate `id` exists, get `profileId` from existing record | `Error` ("Cycle start not found") |
| 4 | Check no duplicate `(profileId, newStartDateIso)` excluding self | `DuplicateCycleStartError` |
| 5 | Update within `realm.write()` | — |
| 6 | Return updated `CycleStart` | — |
| 7 | Caller triggers `syncNotifications()` | — |

**Downstream effects**: Same as delete — prediction chain recalculates.

### `addCycleStart(profileId, startDateIso)` (hardened)

| Step | Action | Error |
|---|---|---|
| 1 | Validate `startDateIso` format (existing) | `Error` (from `assertIsoDate`) |
| 2 | Validate not future date | `FutureDateError` |
| 3 | Validate `profileId` exists (existing) | `Error` ("Profile not found") |
| 4 | Check no duplicate `(profileId, startDateIso)` | `DuplicateCycleStartError` |
| 5 | Insert within `realm.write()` | — |
| 6 | Return new `CycleStart` | — |
| 7 | Caller triggers `syncNotifications()` (existing) | — |

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Duplicate check race condition (two near-simultaneous adds) | Very low | Low | Single-threaded JS + Realm write transaction serialization. No server-side concurrency. |
| Edit creates invalid cycle sequence (date moved to create negative gap) | Low | Low | `computeCycleLengths()` already discards `diff <= 0` gaps. Warn user if gap < 1 day but allow. |
| Notification flap on rapid edit/delete | Low | Low | `syncInFlight` concurrency guard + idempotent IDs. Second sync sees stable state. |
| User accidentally deletes critical entry | Medium | Medium | Confirmation dialog before delete. No undo in MVP — but entry can be re-added manually. |
| Realm `objectForPrimaryKey` returns null on stale ID | Low | Low | Idempotent delete (no-op if not found). Edit throws descriptive error. |
| Timezone edge case for future-date check | Very low | Low | `assertNotFutureDate()` uses local calendar date (same as `syncNotifications`). Near midnight, a date might be "today" in one timezone and "tomorrow" in another — but the check is local-consistent. |
| 2-start users lose predictions (threshold raised from 1 to 2 intervals) | Low | Low | Users with exactly 2 starts previously saw a single-interval prediction. Now they see `null` until third start. Dashboard still shows `cycleDay` and `lastStart`. Predictions improve with the third entry. |
