## Problem Statement

The notification scheduling pipeline has a timezone bug in `todayIso` derivation.

`syncNotifications.ts:53` computes today's date via `formatIsoDate(new Date())`, which
uses `Date.getUTCFullYear/Month/Date`. In negative-UTC-offset timezones (e.g., US Pacific
at UTC-8), this returns tomorrow's date after 4 PM local. The consequence:

1. **Premature filter-out**: A reminder whose fire date is today in local time gets
   compared against a UTC-derived `todayIso` that is already tomorrow — the reminder
   passes the domain filter but the reconciliation layer's `parseIsoLocalDateAtNine()`
   correctly interprets it as 9 AM local today, which is in the past, so it gets skipped.
2. **Missed window**: A reminder that should fire tomorrow at 9 AM local could be
   filtered at the domain layer because `fireDateIso < todayIso` when `todayIso` is
   one day ahead.

Additionally, `syncNotifications()` only runs on cold start and user actions. If the
user crosses a timezone boundary (e.g., travel) and resumes the app, notifications are
not re-reconciled against the new local time. A foreground sync on AppState transition
to "active" closes this gap.

## Scope

### In

- Fix `todayIso` derivation in `syncNotifications.ts` to use local calendar date
- Add `AppState` foreground listener in `App.tsx` to trigger `syncNotifications()` on resume
- ADR 0007 documenting the decision and rationale
- Preserve all existing behavior for cold start, user-action triggers, and idempotency

### Out

- `TIMEZONE_CHANGED` broadcast listener (Android-specific, requires native module)
- `TIME_SET` broadcast listener
- Notification received/response listeners
- Changes to deterministic ID format (`fc-remind-{profileId}-{fireDateIso}T{HH:mm}`)
- Changes to reconciliation logic (`reconcileNotifications.ts`)
- Changes to adapter behavior (`expoNotificationAdapter.ts`)
- Changes to domain plan computation (`notificationPlan.ts`)
- Multi-cycle forecasting or fire-time customization

## Constraints

- Two files modified only: `syncNotifications.ts`, `App.tsx`
- No new dependencies
- No architecture changes
- Deterministic IDs remain unchanged (domain layer date arithmetic is already UTC-correct)
- Reconciliation remains idempotent (same plan → same adapter calls)
- `formatIsoDate()` in `cycleMath.ts` is NOT modified — it correctly uses UTC for date arithmetic. Only the "what is today?" question changes.

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `todayIso` local derivation disagrees with UTC-based `formatIsoDate` used elsewhere | Low | Medium | Only `syncNotifications.ts` changes; domain plan still uses UTC for all date arithmetic. The only effect is widening the "today" filter window to match local perception. |
| AppState listener fires too frequently (rapid background/foreground) | Low | Low | `syncNotifications` is idempotent — duplicate calls produce empty plans. |
| Race between cold-start sync and immediate foreground sync | Low | Low | Both are fire-and-forget with idempotent IDs. Second call sees same tracked IDs and produces empty diff. |
| Local date derivation breaks on DST transition day | Very low | Low | `getFullYear/Month/Date` is DST-aware by definition — it returns the wall-clock date. |
