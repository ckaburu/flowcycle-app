## SECTION 1 — Product Identity Definition

### 1.1 Emotional Tone

FlowCycle is a quiet instrument. It exists to observe, record, and inform — never to interpret, judge, or celebrate. It behaves like a well-made analog clock: always visible, instantly legible, never demanding attention. The interface should feel like opening a journal that already has today's page ready. Information is presented with the same gravity whether the cycle is predictable or irregular. There is no "good" or "bad" state — only data, rendered with calm precision.

### 1.2 What FlowCycle Is NOT

| Anti-Pattern | Rationale |
|---|---|
| Not a wellness coach | No motivational language, no "you're doing great" copy, no streaks, no achievements. Data speaks for itself. |
| Not a social product | No sharing, no community features, no comparisons. Privacy is architectural, not a feature toggle. |
| Not a medical device | No diagnostic language, no health claims, no symptom correlation (unless explicitly requested in a future milestone). |
| Not gamified | No points, badges, confetti, celebration animations, or progress rewards. Logging a cycle start is a neutral record, not an accomplishment. |
| Not playful | No bouncing elements, no cartoon illustrations, no rounded-bubbly aesthetic. The visual language is precise and restrained. |
| Not gendered by default | Profile names are user-defined. No assumptions about who tracks or why. The app never uses gendered pronouns or pink-for-women defaults. (Note: the existing primary color `#D4738C` is dusty rose — this is a deliberate muted tone, not a gendered choice. It stays.) |
| Not a calendar | The app tracks cycle starts as discrete events, not day-by-day journaling. It is not a period diary. |

| Token | Value | Usage |
|---|---|---|
| `sm` | 4 | Inputs, small buttons, chips. |

**Elevation philosophy:**
- Two elevation levels, no more. `elevation.1` for cards. `elevation.2` for modals/sheets.

- The bottom tab bar uses `borderTopWidth: 1` only — no shadow.

### 2.5 Motion Principles

| Principle | Specification |
|---|---|
| Duration range | 150ms–300ms. Nothing shorter (feels instant/jarring). Nothing longer (feels sluggish). |
| Easing | `ease-out` for entries, `ease-in` for exits. `linear` only for progress indicators. |
| Opacity transitions | Preferred over position animations for content changes (error banners, empty states). |
| Ring progress | No animation on mount. Value snaps to computed position. (Existing behavior, retained.) |
| Delete confirmation | Native `Alert.alert` — no custom animation. Platform-consistent. |
| Date picker | Native Android picker — uses system animation, not custom. |
| Screen transitions | React Navigation default (`slide_from_right` for stack, instant for tabs). No custom transitions. |
| Forbidden | No bounce, no spring, no confetti, no pulse, no shake (except PinPad error shake — existing, retained as it serves error feedback). |

### 2.6 Iconography

| Rule | Specification |
|---|---|
| Style | Stroke-based (outline), 24px default, 1.5px stroke weight. |
| Source | Single icon library (recommendation: `@expo/vector-icons` MaterialCommunityIcons or Lucide). Decision deferred to implementation. |

| Color | Icons inherit parent text color. Active tab: `colors.primary`. Inactive: `colors.textMuted`. |

## SECTION 3 — Multi-Profile Interaction Architecture

### 3.1 Active Profile Indicator

**Decision:** Top bar contextual indicator on Dashboard only.

| Aspect | Specification |
|---|---|
| Location | Dashboard header row (existing `ProfileAvatar` + greeting). |
| Format | `ProfileAvatar` (initial circle) + profile name. |
| Tap action | Navigates to Profiles tab. |
| Visibility | Dashboard only. CycleLog shows profile name in subtitle (existing). Settings is profile-agnostic (global). |
| Tab bar | No profile indicator in tab bar. Tab bar remains static (Dashboard, Profiles, Settings). |

**Rationale:** The active profile is already visible on Dashboard. Duplicating it in the tab bar adds visual noise for single-profile users (the majority case). The Profiles tab is the explicit place for profile management.

### 3.2 Profile Switch Flow

```
ProfilesScreen
  ├── tap profile card
  │     ├── saveActiveProfileId(id)         ← AsyncStorage
  │     ├── syncNotifications()             ← reconcile for new profile
  │     └── navigate → CycleLog(profileId)  ← existing behavior
  │
  └── long-press profile card (NEW)
        └── navigate → ProfileDetail(profileId) (NEW screen)
```

**State reconciliation on switch:**
1. `saveActiveProfileId(newId)` persists the selection.
2. `syncNotifications()` fires (existing behavior) — reconciles alarms for the newly active profile.
3. Dashboard refreshes on focus (existing `useFocusEffect`) — picks up new `activeProfileId`.
4. No in-memory cache invalidation needed — all data loads are per-focus.

**Edge case:** If the active profile is deleted, `loadActiveProfileId()` returns the stored ID. `useDashboardData` calls `repository.listCycleStarts(id)` which returns `[]`. Dashboard renders empty state. The user navigates to Profiles tab to select another. No crash, no automatic fallback.

### 3.3 Profile Management Structure

**Current:** ProfilesScreen has create (name input + Add button) and select (card tap → CycleLog). No edit, no delete.

**Target structure:**

| Action | Trigger | Destination |
|---|---|---|
| Create | "Add Profile" button (existing) | Inline — name input at bottom of list. |
| Select | Card tap (existing) | `CycleLog(profileId)` with active profile update. |
| Edit name | Long-press card → ProfileDetail | `ProfileDetail` screen with editable name field. |
| Delete | ProfileDetail → "Delete Profile" button | Confirmation dialog → cascade delete. |

**ProfileDetail screen (NEW):**
- Read-only summary: profile name, created date, cycle start count.
- "Edit Name" — inline editable field with Save/Cancel.
- "Delete Profile" — destructive button at bottom.
- Delete triggers: `repository.deleteProfile(id)` → `syncNotifications()` → if deleted profile was active, clear `activeProfileId`.

**Delete cascade:**
1. `repository.deleteCycleStart()` for all cycle starts belonging to profile.
2. `repository.deleteNotificationPreference(profileId)`.
3. `repository.deleteProfile(id)`.
4. `syncNotifications()` — removes any scheduled alarms for deleted profile.
5. If `activeProfileId === deletedId`: `saveActiveProfileId(null)` → Dashboard shows empty state on next focus.

**No archive option.** Delete is permanent. This aligns with the privacy-first architecture — we do not retain data the user asked to remove.

### 3.4 Visual Profile Differentiation

| Element | Mechanism |
|---|---|
| Avatar | `ProfileAvatar` with deterministic color from `AVATAR_PALETTE` (existing). |
| Card accent | Left border (3px) using the profile's avatar color on profile cards in ProfilesScreen. |
| Dashboard header | Avatar + name (existing). |
| CycleLog subtitle | Profile name text (existing). No color accent — the screen context is already established by navigation. |

**Rules:**
- Profile colors are derived from the name hash (existing `avatarColorIndex`). Not user-selectable.
- The palette is muted by design (8 colors, all desaturated). This is intentional.
- No profile-specific themes. The entire app uses a single color system regardless of active profile.

### 3.5 Notification Reconciliation on Profile Switch

**Current behavior (v0.4.2):** `syncNotifications()` fires on profile switch in `ProfilesScreen.onSelectProfile()`. The sync reads the active profile's notification preference and cycle data, computes the plan, and reconciles against tracked IDs.

**Gap:** If Profile A has a scheduled notification and the user switches to Profile B, Profile A's notification remains scheduled (because `syncNotifications` only operates on the active profile). This is **correct behavior** — notifications are per-profile, and switching profiles does not cancel other profiles' reminders.

**Clarification for implementation:**
- `syncNotifications()` operates on the **active profile only** (reads `activeProfileId` from AppState).
- Profile deletion (new in this milestone) must explicitly cancel the deleted profile's notifications via `adapter.cancel(id)` for each tracked ID matching the deleted profile.
- No "notification for all profiles" mode. Each profile is independent.

## SECTION 5 — Cycle Log Redesign Concept

### 5.1 Entry Card Structure

**Current:** `AppCard` containing either read-mode (date text + Edit/Delete buttons) or edit-mode (AppInput + Save/Cancel buttons).

**Target:**

```
┌─────────────────────────────┐
│  2026-02-01                 │  ← date, body variant
│  Cycle #3 · 28 days        │  ← caption: cycle number + interval length
│                 [Edit] [Del]│  ← ghost + danger buttons
└─────────────────────────────┘
```

**Changes from current:**
- Add cycle number and interval length as caption metadata. This requires computing `computeCycleLengths()` and mapping each entry to its interval. Pure display — no new domain logic needed, just wiring the existing `computeCycleLengths` output into the card.
- First entry shows "Cycle #1" with no interval (no prior reference point).

### 5.2 Edit Interaction: Inline Retained

**Decision:** Keep inline editing (existing pattern).

**Rationale:**
- Modal editing adds navigation complexity for a single-field edit.
- Inline editing is already implemented and tested.
- The edit surface is small (one date field) — modal is over-engineered.
- Inline pattern is consistent with the "no gimmicks" principle.

**Refinement:**
- Replace `AppInput` text field with date picker trigger in edit mode (see 5.3).
- Save/Cancel buttons remain.

### 5.3 Date Picker

**Decision:** Native Android date picker (via `@react-native-community/datetimepicker` or Expo equivalent).

**Interaction flow:**
1. User taps "Add Cycle Start" or "Edit" on an entry.
2. Native date picker opens as a modal dialog (Android `DatePickerDialog`).
3. User selects date → picker dismisses → date is committed.
4. For "Add": date is submitted immediately (no intermediate text input).
5. For "Edit": date populates the inline edit field → user confirms with "Save".

**Constraints:**
- Max date: today (future-date rejection already enforced at repo layer, picker also restricts).
- Min date: none (users may log historical data).
- Default date: today for "Add", current entry date for "Edit".

**What this replaces:**
- `AppInput` with `placeholder="YYYY-MM-DD"` for adding new entries.
- `AppInput` with `placeholder="YYYY-MM-DD"` in edit mode.

### 5.4 Error Display Strategy

**Retained:** `ErrorBanner` at top of screen for all errors.

| Error | Source | Message |
|---|---|---|
| Invalid date format | Client validation (retained as fallback even with date picker) | "Date must be in YYYY-MM-DD format." |
| Duplicate date | `DuplicateCycleStartError` from repo | "A cycle start already exists on {date} for this profile." |
| Future date | `FutureDateError` from repo | "Cycle start date cannot be in the future." |
| Load failure | Network/storage error | "Failed to load cycle data." |

**No inline field-level errors.** The date picker eliminates format errors. Duplicate and future-date errors come from the repo layer and are displayed at the screen level.

### 5.5 Delete Confirmation Pattern

**Retained:** Native `Alert.alert` with "Cancel" (default) and "Delete" (destructive).

**Rationale:**
- Platform-consistent behavior.
- No custom modal component needed.
- Destructive action styling handled by the OS.
- Users recognize the pattern from every other Android app.

**No swipe-to-delete.** Swipe gestures are hidden affordances — they contradict the "predictability > magic" principle.

### A.1 Dashboard Layout Evaluation: Baseline vs Alternative

**Question:** Is the existing vertical-stack layout the right structure, or should the dashboard reorganize information hierarchy?

**Baseline (current v0.4.2):**

```
┌─────────────────────────────┐
│  [A] Hi, Name               │  header
│                             │
│         ┌───────┐           │
│         │  25   │           │  ring (hero)
│         │of 28d │           │
│         └───────┘           │
│                             │
│  ┌─────────────────────┐    │
│  │ Last start   02-01  │    │  info card (3 rows)
│  │ Typical      28 d   │    │
│  │ Next est.    03-01  │    │
│  └─────────────────────┘    │
│                             │
│  [ Log Period Start ]       │  primary CTA
│   View Cycle Log            │  secondary link
└─────────────────────────────┘
```

**Alternative evaluated — ring + prediction in single hero unit:**

```
┌─────────────────────────────┐
│  [A] Hi, Name               │
│                             │
│  ┌─────────────────────┐    │
│  │    ┌───────┐        │    │
│  │    │  25   │ Day 25 │    │  hero card: ring + text
│  │    │of 28d │ of 28  │    │  side-by-side
│  │    └───────┘        │    │
│  │  Next: Mar 1 (4d)   │    │  prediction inline
│  └─────────────────────┘    │
│                             │
│  [ Log Period Start ]       │
│   View Cycle Log            │
└─────────────────────────────┘
```

**Decision: Retain baseline.**

| Factor | Baseline | Alternative |
|---|---|---|
| Information density | Spread — easy to scan | Compressed — faster to read but harder to parse at glance |
| Ring prominence | Standalone hero, high visual weight | Co-located with text, competes for attention |
| State transitions | Info card hides cleanly when 0 cycles; empty state fills the gap naturally | Hero card must handle mixed content/empty states internally — more complex |
| Implementation cost | Zero (existing) | New layout component, responsive breakpoints for ring+text alignment |
| Alignment with tone | Calm — each section breathes | Denser — efficiency-oriented, less calm |
| Prediction threshold states | 0/1/2 cycles: info card shows `—` values, ring shows day count. Clear separation between "what is" (ring) and "what we know" (card) | Mixed: ring and prediction in same container — unclear what to show when prediction is unavailable |

**Supplementary rationale:** The baseline layout has a natural information cascade: identity (header) → current state (ring) → derived knowledge (card) → action (button). This top-down hierarchy matches how the user approaches the screen: "Who am I tracking? → Where am I? → What does the pattern suggest? → What can I do?" Collapsing ring and prediction into a single unit breaks this cascade by mixing observed state with computed inference.

The baseline also degrades gracefully across the four prediction threshold states. With 0 cycles, the ring shows `—` and the info card is hidden entirely — the screen is clean and unburdened. With 1–2 cycles, the ring shows a day count but the info card shows `—` for prediction fields — the user sees exactly what is known and what isn't. The alternative layout would need conditional rendering within the hero card, adding visual complexity for the same information.

### A.2 Inline Editing vs Modal Editing: Explicit Justification

**Supersedes:** Section 5.2 rationale (retains same decision, deepens justification).

**Decision: Inline editing retained.** The following is a structured evaluation, not just a list of bullet points.

#### Evaluation matrix

| Criterion | Inline | Modal | Weight |
|---|---|---|---|
| Edit surface size | 1 field (date) | 1 field (date) | — |
| Context preservation | User sees the entry's position in the list while editing. Adjacent entries provide reference ("Was it before or after this one?"). | User loses list context. Must remember where the entry sits. | High — cycle dates are relative data. Context matters. |
| Navigation cost | Zero — tap Edit, field appears in-place. | Push screen or overlay. Dismiss to return. Two transitions for one field. | Medium |
| Error recovery | Error banner appears above the list. The erroring entry remains visible with its draft value. User can correct immediately. | Error appears on the modal. User must fix or dismiss and re-navigate. | Medium |
| Implementation state | Fully implemented, tested (v0.4.2). `editingId`/`editDateInput` state, Save/Cancel buttons. | Not implemented. Requires new screen or overlay component, navigation params, state passing. | Low (sunk cost is not a design argument, but it matters for scope) |
| Multi-entry editing | Only one entry editable at a time (`editingId` is singular). Clear constraint. | N/A — modals are inherently single-entry. Equivalent. | Neutral |
| Date picker interaction | Date picker opens as overlay from the inline card. Entry card shows selected date on return. | Date picker opens from within the modal. Equivalent interaction, but nested inside another overlay — feels heavier. | Low |
| Accessibility | Tab order: list → edit field → Save/Cancel. Linear, predictable. | Modal traps focus. Requires proper focus management on open/close. More implementation work for equivalent accessibility. | Medium |
| "Predictability > magic" alignment | Edit/Save/Cancel visible inline — no hidden state. | Modal appearance is a mode shift. The list "goes away" temporarily. | High — this is a core product principle. |

**Verdict:** Inline wins on context preservation (high weight), navigation cost, and predictability alignment. Modal wins on nothing — it is strictly more complex for a single-field edit with no countervailing benefit.

**The one scenario where modal would win:** If editing expanded to multiple fields (date, notes, flow intensity, symptoms). A multi-field edit form justifies a dedicated surface. This is explicitly out of scope for the current data model (`CycleStart` has only `startDateIso`). If the data model expands, this decision should be revisited.

```
│                 [Save] [✕]  │
└─────────────────────────────┘

User taps the date display → native DatePickerDialog opens.
User selects new date → dialog dismisses → date display updates.
User taps [Save] → commit. Or [✕] → revert.
```

Key change: the edit mode no longer shows a raw `AppInput`. It shows the selected date as a styled tappable element that triggers the native picker. This eliminates the text input entirely for editing — the user never types a date string.

### A.3 Active Profile Context on Mutation Screens

**Extends:** Section 3.1 (which defined Dashboard-only profile indicator).

**Problem:** Section 3.1 states the active profile indicator lives on Dashboard only, with CycleLog showing the profile name in the subtitle. But the user's refinement asks: is the profile context *visible enough* on every screen where data mutation can occur?

**Audit of mutation screens:**

| Screen | Mutations | Current Profile Context | Gap? |
|---|---|---|---|
| DashboardScreen | Quick-log (add cycle start) | Avatar + name in header row. | No — clear and prominent. |
| CycleLogScreen | Add, edit, delete cycle starts | `profile.name` in subtitle text (`AppText variant="subheading"`). | Marginal — the subtitle is muted-color text. It is readable but not prominent. A user with multiple profiles might not notice which profile they're editing. |
| ProfilesScreen | Create profile, switch active profile | Profile list is the screen itself. Active profile has no visual indicator beyond being tappable. | Yes — there is no indicator of *which* profile is currently active. All cards look identical. |
| SettingsScreen | Toggle notifications, change days-before | No profile context visible. | Yes — but settings mutations are profile-scoped (notification preference is per-profile). The user doesn't know which profile's notifications they're configuring. |

**Amendments:**

**A. CycleLogScreen — Add profile avatar to header.**

```
┌─────────────────────────────┐
│  Cycle Log                  │  ← heading (existing)
│  [A] Sarah                  │  ← avatar + name (enhanced from plain text)
│                             │
│  [entries...]               │
```

Replace the plain `AppText variant="subheading"` subtitle with `ProfileAvatar` (size 24) + `AppText variant="subheading"`. The avatar provides a color-coded visual cue that is faster to parse than reading the name.

**B. ProfilesScreen — Mark active profile.**

Add a visual indicator to the active profile's card:

```
┌─────────────────────────────┐
│  Sarah                   ●  │  ← filled dot (primary color) = active
│  ID: 1                      │
└─────────────────────────────┘
┌─────────────────────────────┐
│  Maria                      │  ← no dot = inactive
│  ID: 2                      │
└─────────────────────────────┘
```

The active indicator is a small filled circle (`View` with `width: 8, height: 8, borderRadius: 4, backgroundColor: colors.primary`). No text label ("Active") — the dot is sufficient and doesn't add translation burden.

**C. SettingsScreen — Show active profile context in Notifications section.**

```
Notifications
  Period Reminders for Sarah        [toggle]
  Remind me          2 days before  [tap to cycle]
```

Append the active profile name to the "Period Reminders" label. This makes the scope of the setting explicit without adding a separate header element.

### A.4 Limited Undo Pattern for Destructive Actions

**Extends:** Section 5.5 (delete confirmation) and Section 3.3 (profile deletion).

**Problem:** The base document defines delete as immediate and permanent with only a native `Alert.alert` confirmation gate. This is a one-gate-then-gone pattern. The refinement asks: should there be a brief undo window after destructive actions?

**Evaluation:**

| Pattern | Description | Pros | Cons |
|---|---|---|---|
| Confirm-only (current) | `Alert.alert` → Delete → gone | Simple. Platform-native. No temporary state. | No recovery after confirmation. User who taps "Delete" by muscle memory loses data. |
| Undo snackbar | Delete executes immediately. Snackbar appears at bottom: "Deleted. [Undo]". 5-second window. If undo tapped, data is restored. If timer expires, delete is permanent. | Recovery window. Feels forgiving. Standard Android pattern (Gmail, Keep). | Requires soft-delete + deferred hard-delete. Complicates notification reconciliation (do we cancel alarms during the undo window?). |
| Undo with deferred execution | Delete is *staged* but not executed. Snackbar appears. If undo tapped, staging is cleared. If timer expires, delete executes for real. | Cleaner — no need to restore data. Notifications stay until commit. | UI must hide the "deleted" entry during the undo window. More complex state management. |

**Decision: Undo snackbar with deferred execution, for cycle start deletion only.**

**Scope:**
- Cycle start deletion: **yes** — this is the most common destructive action, and the most likely to be accidental (small target, multiple entries in a list).
- Profile deletion: **no** — profile deletion is rare, high-stakes, and already gated behind navigation to ProfileDetail + explicit "Delete Profile" button + Alert.alert confirmation. Three gates is sufficient. Adding undo to a rare, heavily-gated action adds complexity without proportional benefit.

**Behavior specification:**

```
1. User taps [Delete] on cycle entry card.
2. Alert.alert confirmation dialog appears (existing).
3. User confirms "Delete".
4. Entry is visually removed from the list (hidden, not destroyed).
5. Snackbar appears at screen bottom:
     "Cycle start removed. [Undo]"
   Duration: 5 seconds. Auto-dismiss.
6. If user taps [Undo] within 5 seconds:
     - Entry reappears in the list.
     - Snackbar dismisses.
     - No repo mutation occurred. No notification resync needed.
7. If 5 seconds elapse without undo:
     - repository.deleteCycleStart(id) executes.
     - fireAndForgetSync() triggers.
     - Snackbar dismisses.
```

**Key property:** The repo mutation is deferred. During the undo window, the entry is hidden in the UI but still exists in the database. This means:
- No data is lost if the app crashes during the undo window.
- Notifications are not disrupted during the undo window (alarms remain scheduled).
- If the user navigates away during the undo window, the delete commits (no orphaned hidden entries).

**Implementation hint (for Milestone 3, not this document):**
- `pendingDeleteId: number | null` state in CycleLogScreen.
- `setTimeout` with 5000ms delay.
- Snackbar is a simple `View` positioned absolutely at the bottom of `ScreenContainer`, with opacity fade-in/fade-out (within the 150–300ms motion budget).
- Cleanup on unmount: if `pendingDeleteId` is non-null, commit the delete.

### A.5 Per-Profile Accent Differentiation Strategy

**Supersedes:** Section 3.4 (retains avatar color mechanism, refines application surface).

**Problem:** Section 3.4 defines profile differentiation via avatar color and a left-border accent on profile cards. The refinement asks: should per-profile accent extend further, and what are the boundaries?

**Existing color mechanism:**

```typescript
// avatarColor.ts
AVATAR_PALETTE = [
  "#D4738C",  // dusty rose
  "#8FB5A3",  // sage green
  "#E8C87A",  // warm gold
  "#7BAFD4",  // soft blue
  "#C49BD4",  // lavender
  "#D4A07B",  // warm tan
];
avatarColorIndex(name) → deterministic hash → palette index
```

Six colors, all muted, all derived deterministically from the profile name. The user does not choose.

**Accent application surfaces (expanded from Section 3.4):**

| Surface | Accent | Mechanism |
|---|---|---|
| ProfileAvatar | Background fill | Existing — `AVATAR_PALETTE[avatarColorIndex(name)]` |
| ProfilesScreen card | Left border (3px) | Defined in Section 3.4, unchanged |
| ProfilesScreen active indicator | Filled dot uses profile's accent color (not `colors.primary`) | Refined from A.3 — the active dot matches the profile, not the app primary |
| Dashboard header avatar | Background fill | Existing — same as ProfileAvatar |
| CycleLogScreen header avatar | Background fill (24px size) | New per A.3 — uses same mechanism |
| CycleLog entry cards | No accent | Intentional — entry cards are data records, not profile-branded surfaces |
| Cycle ring | No accent — always `colors.primary` or `colors.warning` | Intentional — the ring represents cycle state, not profile identity |
| Settings | No accent | Intentional — settings is profile-agnostic UI |
| Tab bar | No accent | Intentional — navigation is global |
| Notifications | No accent | Notifications use system chrome, not app theming |

**Boundaries — what the profile accent is NOT:**

| Rule | Rationale |
|---|---|
| The accent never replaces `colors.primary` for interactive elements | Buttons, links, toggles use `colors.primary` regardless of profile. Profile accent is identity, not interaction. |
| The accent never colors text | Profile accent is always a background fill or border. Text remains `colors.text` or `colors.primaryFg` (on accent background). |
| The accent never appears on data surfaces | Cycle entries, info cards, and prediction text are neutral. Data is objective — it does not "belong to" a color. |
| The accent is always the same size/weight | 3px border, 24–40px avatar circle, 8px dot. No screen uses a larger accent surface (e.g., full-width header bar in profile color). |
| The palette is not user-configurable | Deterministic derivation ensures consistency without preference UI. If two profiles hash to the same color, that's acceptable — the name text disambiguates. |

**Active indicator refinement (amends A.3):**

The filled dot on ProfilesScreen uses the profile's own accent color rather than `colors.primary`. This means each profile card has two accent signals: left border (3px, profile color) and active dot (8px circle, profile color) — but only the active profile has the dot. This is subtle enough to not feel "themed" but provides instant recognition when the list has 3+ profiles.

```
┌─[rose]─────────────────────┐
│  Sarah                 (●) │  ← dot in rose = active
│  ID: 1                     │
└────────────────────────────┘
┌─[blue]─────────────────────┐
│  Maria                     │  ← no dot = inactive
│  ID: 2                     │
└────────────────────────────┘
┌─[gold]─────────────────────┐
│  Alex                      │  ← no dot = inactive
│  ID: 3                     │
└────────────────────────────┘
```
